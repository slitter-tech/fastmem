Route single reads through the C extension: 2.4x on point reads

read() went through ctypes and paid the Python -> C boundary cost on
every call. The extension already had one() for exactly this, but it was
never wired into the public path.

- read() now uses one() / one_or() when the extension is present and
  falls back to ctypes otherwise.
- one() accepts a memoryview, so Python hands over its reusable buffer
  directly instead of building a ctypes c_char array per call to match
  an argument type. The scratch buffer's memoryview is cached at open.
- one_or() is new: it builds the bytes object in C, skipping a second
  copy of the data that a Python-side string_at would make.
- struct.Struct objects are now precompiled at import time; previously
  struct.unpack_from looked the format up in its cache on every read.

Foreign process, microseconds per 8-byte read:
  read() success          7.33 -> 3.07
  read(or_none=True)      6.13 -> 2.95
  read(as_='int')         6.69 -> 3.80

Also fixes a latent bug in the test suite: seven buffers were created
as `_, addr = cbuf(...)`, dropping the only reference to them. The GC
freed the memory and reads from the stale address returned whatever now
occupied it, which made the suite flaky in a way that had nothing to do
with the code under test. Each buffer now keeps its own name.

Batches and grouping are unchanged: 3.1-3.6x and 20.8x respectively.
